## Context

`app/src/pricing.ts` вже дає `subtotalKopecks`, `shippingKopecks`, `tierPercent` — стабільний, незмінний контракт. Знижковий рушій — новий, чистий модуль поруч. Усі рішення щодо неоднозначностей (порядок застосування, округлення, помилки промокодів) уже зафіксовані в `docs/spec/pricing-discounts.md` і в `specs/pricing-discounts/spec.md`; цей документ описує лише порядок обчислень, потрібний, щоб два різні прогони дали однаковий результат.

## Goals / Non-Goals

**Goals:**
- Один точний алгоритм обчислення `priceOrder`, що відтворює числа з усіх AC-1…AC-11 дослівно, до копійки.
- Помилки одного промокоду (прострочений, невідомий, нижче мінімуму) не блокують застосування інших валідних промокодів у тому ж запиті.

**Non-Goals:**
- Зміна чи розширення `pricing.ts` / `types.ts`.
- Персистентність, зберігання чи видача промокодів — вхід уже дано як `Coupon[]`.

## Decisions

**Один прохід, п'ять кроків, з округленням `floor()` після кожного кроку, що дає копійки:**

1. `base = subtotalKopecks(order)` — база знижок; доставка в неї не входить (Requirement "Доставка поза базою знижки").
2. Знижка за рівнем: `tierDiscount = floor(base * tierPercent(order) / 100)`. Якщо `tierPercent === 0`, крок пропускається (`tierDiscount = 0`), без запису в помилки.
3. `remaining = base - tierDiscount` — це і є залишок, від якого рахуються промокоди (Requirement "Послідовне застосування").
4. Обробка промокодів окремим циклом, у два проходи за `kind` (спершу всі `fixed` за порядком `order.coupons`, потім усі `percent` за тим самим порядком — Requirement "Комбінування кількох промокодів"):
   - Для кожного коду з `order.coupons`: знайти відповідний `Coupon` за `code`. Не знайдено → `couponErrors.push({code, message: "Промокод XXXX не знайдено"})`, пропустити.
   - Перевірити `expiresAt`: прострочено, якщо поточна дата пізніша за кінець доби `expiresAt` → помилка "Промокод XXXX прострочено", пропустити.
   - Перевірити `minSubtotalKopecks` відносно початкового `base` (до будь-яких знижок, Requirement "Мінімальна сума") → помилка з текстом мінімуму, пропустити.
   - Обчислити базу для цього промокоду:
     - без `category`: поточний `remaining`.
     - з `category`: окремий трекер `categoryRemaining[category]`, ініціалізований сумою рядків цієї категорії (без відрахування `tierDiscount` — Requirement "Промокод, обмежений категорією товару"), що зменшується кожним застосованим до цієї категорії промокодом.
   - `discount = kind === "fixed" ? min(value, base) : floor(base * value / 100)`; відняти від відповідної бази (`remaining` і, якщо категорійний, від `categoryRemaining[category]` та додатково від глобального `remaining`, щоб рядки категорії не знижувались двічі — глобальний `remaining` завжди зменшується на кожну застосовану знижку промокоду, категорійний трекер існує лише для розрахунку бази наступного категорійного промокоду).
   - Накопичити `couponDiscountKopecks += discount`.
5. `itemsTotal = max(0, remaining)` (Requirement "Підсумок не може бути відʼємним"); `total = itemsTotal + shippingKopecks(order)`.

**Чому два проходи (fixed → percent), а не один за порядком введення:** так узгоджено в D-3/AC-11 — бізнес хоче, щоб фіксовані знижки завжди «йшли першими» незалежно від того, який код клієнт ввів раніше. Альтернатива (строго за порядком введення) відхилена, бо суперечить прийнятому рішенню в специфікації.

**Чому категорійна база не віднімає `tierDiscount`:** рівнева знижка рахується від усього замовлення й не має природного способу розподілу по категоріях без довільного правила пропорції, якого тікет не просив (D-12).

## Risks / Trade-offs

- [Дві незалежні бухгалтерії (`remaining` і `categoryRemaining`) можуть розійтися при помилці в реалізації] → покрити тестом AC-3 (два категорійні промокоди) окремо від AC-11 (fixed+percent без категорії), щоб розбіжність впала на конкретний тест.
- [`floor()` на кожному кроці, а не в кінці, менш інтуїтивний для рев'юера] → залишити коментар-посилання на AC-9 у коді безпосередньо біля функції округлення.
