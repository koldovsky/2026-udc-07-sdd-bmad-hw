## Context

Мотивація — див. `proposal.md` → Why. Вимоги до поведінки —
`specs/order-discounts/spec.md`. Тут лише те, як це побудувати.

Обмеження, які формують підхід:

- `app/src/types.ts` і `app/src/pricing.ts` — засіяний контракт: сигнатури й
  поведінку `lineTotalKopecks`, `subtotalKopecks`, `shippingKopecks`,
  `tierPercent` змінювати не можна. Нова логіка надбудовується над ними.
- Домен не має рантайм-залежностей і не повинен їх набути.
- Суми — цілі копійки. Числа з рухомою комою заборонені для грошей.
- `Coupon.expiresAt` — рядок ISO; `Order.coupons` — рядки в порядку введення.
  Самих обʼєктів купонів у `Order` немає, тож каталог має надходити ззовні.

## Goals / Non-Goals

**Goals:**

- Одна чиста функція як єдина точка входу в ціноутворення зі знижками.
- Порядок обчислень зафіксований у коді так, щоб рішення зі специфікації не
  можна було переплутати місцями непомітно.
- Пріоритет причин відмови — **дані**, а не порядок `if`-ів.
- Кожен сценарій зі специфікації перевіряється тестом без моків і без
  підміни системного часу.

**Non-Goals:**

- Валідація каталогу купонів (`percent` у 0–100, `fixed` ≥ 0, коректний ISO) —
  вважається гарантією викликача.
- Кешування, індексація каталогу, оптимізація під великі каталоги.
- Персистентність, аналітика застосованих купонів, тексти для користувача.

## Decisions

**D-A. Новий модуль `app/src/discounts.ts`, а не розширення `pricing.ts`.**
`pricing.ts` захищений guardrail-ом і покритий засіяними тестами; окремий файл
робить межу «що можна чіпати» очевидною при рев'ю. Публічний API реекспортується
через `app/src/index.ts`. Альтернатива — дописати в `pricing.ts` — відхилена:
diff по захищеному файлу довелося б перевіряти рядок за рядком.

**D-B. Округлення — цілочисельна формула, а не `Math.round`.**

```ts
const percentOf = (base: number, percent: number): number =>
  Math.floor((base * percent + 50) / 100);
```

`Math.round(base * percent / 100)` дало б той самий результат на типових сумах,
але ділення на 100 створює число з рухомою комою, тобто саме те, чого вимога
округлення й забороняє. Цілочисельна форма точна за побудовою і не залежить від
подвійної точності. `+50` перед діленням — це і є «половина вгору».

**D-C. Придатність купона — впорядкований список правил, а не ланцюг `if`.**
Пріоритет причин (`unknown` → `expired` → `min_subtotal_not_met` →
`category_absent` → `no_effect` → `not_best`) кодується порядком елементів у
масиві предикатів. Причина відмови стає першим спрацьованим правилом. Так
пріоритет видно в одному місці й неможливо змінити його випадковою
перестановкою умов. Альтернатива — вкладені `if`-и — відхилена саме тому, що
там порядок неявний.

**D-D. Момент оцінки `now: Date` — параметр, а не `Date.now()` всередині.**
Робить функцію чистою й дозволяє перевірити межу терміну дії з точністю до
мілісекунди (сценарій AC-6) без підміни таймерів. Ціна — зайвий аргумент у
кожного викликача; вважаємо це прийнятним обміном.

**D-E. Каталог купонів — масив у параметрі, зіставлення лінійним пошуком.**
Замовлення на чекауті має одиниці кодів, каталог — десятки; складність
O(кодів × каталогу) неістотна. `Map` зробив би сигнатуру менш очевидною для
викликача, який просто має список купонів кампанії.

**D-F. Вибір переможця — один прохід із суворим «більше», а не сортування.**
Стабільний тай-брейк «перший введений» виходить сам собою: наступний кандидат
замінює поточного лише за строго більшої знижки. Сортування вимагало б окремо
гарантувати стабільність.

**D-G. Обмеження знижки застосовується один раз — на рівні бази купона.**
Фіксований купон обмежується своєю базою (сумою категорії після рівня або
залишком після рівня). Другого обмеження — підсумкової знижки залишком після
рівня — **не потрібно**.

> ⚠️ **Виправлено під час Task C.** Початкова редакція цього рішення вимагала
> другого обмеження й обґрунтовувала його тим, що база категорійного купона
> «теоретично може розійтися із загальним залишком на копійку через
> округлення». Це неправда. Функція `f(x) = x − percentOf(x, p)` неспадна:
> `f(x+1) − f(x) = 1 − [0 або 1] ≥ 0`, бо крок `percentOf` при `p ≤ 100` не
> перевищує 1. Оскільки сума категорії ніколи не більша за суму замовлення,
> база категорійного купона ніколи не перевищує залишок після рівня. Перебір
> усіх комбінацій для `p ∈ {0, 5, 10}` і сум до 20 000 копійок дав 0
> контрприкладів. Друге обмеження було мертвим кодом: жоден AC його не вимагав
> і жоден тест не падав після видалення. Прибрано з реалізації, рішення
> переписано.

**D-H. Повертається розкладка, а не число.**
`PriceBreakdown` містить обидві знижки окремо, застосований код і список
відхилених із причинами. Це прямий наслідок вимоги «жоден введений код не зникає
без пояснення»: одне число не може її задовольнити.

**D-I. Тести названі за ID сценаріїв (`AC-1`…`AC-16`).**
Звʼязок зі специфікацією видно у виводі vitest, а таблиця простежуваності
будується механічно. Фабрики `item()` / `order()` беруться з наявного
`pricing.test.ts` за зразком, щоб стиль тестів не роздвоювався.

## Risks / Trade-offs

- **Некоректний `expiresAt` у каталозі → `Date.parse` дає `NaN`.** Будь-яке
  порівняння з `NaN` хибне, тож купон не пройде перевірку «дійсний» і буде
  відхилений як `expired`. → Відмова в безпечний бік, але причина вводить в
  оману. Пом'якшення: валідація каталогу явно поза скоупом, поведінку фіксуємо
  тут, щоб вона не виглядала випадковою.
- **Округлення на кожному кроці накопичує розбіжність із «точною» знижкою.**
  На великих сумах послідовне округлення може відрізнятися від одноразового на
  1–2 копійки. → Прийнято свідомо: натомість поля розкладки сходяться в підсумок
  без залишку, що важливіше для бухгалтерії та для довіри до чека.
- **`percentOf` перемножує до ділення.** При сумі понад ~9·10¹³ копійок
  добуток вийде за межі безпечних цілих. → Нереалістично для чекауту (це
  ~900 млрд грн на одне замовлення); фіксуємо як відоме обмеження, а не
  захищаємось кодом, якого специфікація не просила.
- **Категорійний купон рахується від суми категорії після рівня.** Це неочевидно
  при читанні коду й легко «спростити» до суми категорії без рівня. → Сценарій
  AC-14 підібраний так, що таке спрощення дає 89 400 замість 89 500 і тест падає.

## Migration Plan

Зміна суто адитивна: нових залежностей немає, наявні функції та їхні тести не
торкаються, схем даних немає. Розгортання — звичайний реліз бібліотеки.
Відкат — перестати викликати `priceOrder`: попередня поведінка ціноутворення
лишається доступною через незмінені `subtotalKopecks` і `shippingKopecks`.
