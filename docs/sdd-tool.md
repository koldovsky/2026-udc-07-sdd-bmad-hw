# Task B — SDD-інструмент

## Який інструмент

**OpenSpec 1.12.0** (`@fission-ai/openspec`, Node CLI). Обрано з практичних
міркувань: репо вже на Node, тож інструмент не тягне за собою `uv`/Python, як
Spec Kit чи BMAD. Схема — дефолтна `spec-driven` (`proposal → specs → design →
tasks`).

## Що він згенерував

| Команда | Що зʼявилось у репо |
|---|---|
| `openspec new change add-discount-engine` | `openspec/changes/add-discount-engine/` — `README.md`, `.openspec.yaml` (schema, `created`, `goal`) |
| `openspec instructions <artifact> --change …` | Збагачений промпт-контракт на кожен артефакт (не файл, а інструкція, за якою пишеш) |
| написано за цими інструкціями | `proposal.md`, `specs/discount-engine/spec.md` (дельта-формат: `## ADDED Requirements` → `### Requirement:` → `#### Scenario:` з `WHEN/THEN`), `design.md`, `tasks.md` |
| `openspec validate add-discount-engine --strict` | Структурна перевірка; двічі впіймала помилки під час чернетки |
| `openspec status --change add-discount-engine` | Прогрес `4/4 artifacts`, граф залежностей (specs blocked-by proposal, tasks blocked-by specs+design) |

Усі артефакти закомічені в `openspec/changes/add-discount-engine/`.

## Що він дав **понад** звичайну markdown-специфікацію

1. **Ланцюг артефактів із гейтингом залежностей.** `proposal → specs → design →
   tasks`, і `status` не дасть вважати `tasks` готовими, поки немає `specs` і
   `design`. Це силоміць розводить «навіщо / що / як» по окремих документах
   замість одного полотна, де все злипається.
2. **Машинна перевірка структури.** `validate --strict` падає, якщо у сценарію 3
   `#` замість 4, якщо в реквайрмента немає жодного сценарію, якщо `## Purpose`
   нової здатності коротший за 50 символів. Моя рукописна спека такого
   запобіжника не має. Тут це реально спрацювало — я двічі отримав помилку на
   малформованих сценаріях і полагодив до коміту.
3. **Опінієйтед-інструкції на кожен артефакт.** `openspec instructions specs`
   каже речі на кшталт «spec — це контракт поведінки, а не план реалізації;
   якщо реалізацію можна змінити, не змінивши видимої поведінки, це не належить
   до спеки». Це підштовхнуло чистіше розділити `design.md` (як рахуємо
   `remaining`) і `spec.md` (що видно ззовні).
4. **Дельта-модель + archive.** `ADDED / MODIFIED / REMOVED Requirements` і
   `openspec archive`, який вливає завершену зміну в канонічний
   `openspec/specs/`. Для одноразової ДЗ це накладні витрати; у живому репо, де
   таких змін десятки проти спільного дерева специфікацій, — це і є сенс
   інструмента.
5. **Легкий трекінг.** `openspec list` / `status` дають картину прогресу без
   окремої дошки задач.

## Що довелося робити руками (інструмент за тебе не думає)

- **Усі рішення** щодо неоднозначностей (D-1..D-21). OpenSpec жодного разу не
  запропонував ані порядку складання знижок, ані напряму округлення, ані бази
  знижки — він дає **порожні** секції шаблону. Найважча частина Task A —
  ідентична робота з інструментом і без нього.
- **Усі конкретні числа** у сценаріях. `validate` перевіряє форму, а не
  арифметику: він спокійно провалідував спеку ще до того, як я перевірив хоч
  один підсумок вручну.
- **`docs/traceability.md`, тести, звʼязок AC ↔ код** — усе поза OpenSpec.
- **Межі здатності** (`discount-engine` — одна capability чи кілька): інструмент
  спитав у шаблоні, відповідь — на мені.
- **Синхронізація двох джерел істини.** Тепер і `docs/spec/pricing-discounts.md`,
  і `openspec/.../spec.md` описують ту саму поведінку. Тримати їх узгодженими —
  ручна робота; інструмент про існування першого файлу не знає.

## Чесний висновок

На фічі такого розміру OpenSpec додав **дисципліну процесу і структурний
лінтер**, а не інсайт. Двадцять одне рішення — власне суть задачі — були б тим
самим обсягом роботи без нього. Його цінність накопичувалася б у репозиторії з
багатьма змінами проти спільного дерева специфікацій (цикл
`validate → archive → delta`); тут це переважно церемонія — але дешева, і
`--strict`-валідатор двічі виправив малформовані сценарії, поки я писав.
Тобто: тримати не для «think for me», а для «не дай написати структурно
криву специфікацію і не дай перескочити крок».
