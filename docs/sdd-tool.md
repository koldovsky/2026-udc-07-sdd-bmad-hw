# Task B — SDD-інструмент

**Інструмент:** [OpenSpec](https://github.com/Fission-AI/OpenSpec) v1.11.0
(`npm install -g @fission-ai/openspec@latest`)
**Схема воркфлоу:** `spec-driven` (proposal → specs → design → tasks)
**Вхід:** `docs/spec/pricing-discounts.md` (моя специфікація з Task A)
**Дата прогону:** 2026-09-02

---

## 1. Чому саме OpenSpec

У системі стояли всі три (`openspec`, `specify`, `uv` — перевірено `which`), тож
вибір був не за доступністю, а за доцільністю:

- це Node-CLI на TypeScript-репо — жодного другого рантайму заради чотирьох
  markdown-файлів;
- він **валідує** артефакти (`openspec validate --strict`), а не лише
  скафолдить їх. Spec Kit і BMAD дають структуру й промпти, але не мають
  еквівалента «ця специфікація формально невалідна»;
- BMAD **уже стоїть у цьому репо** (`_bmad/`, `.claude/skills/`, `.agents/skills/`)
  — використати його як «другий інструмент» у Task E дає чесніше порівняння,
  ніж прогнати обидва тут.

## 2. Що зроблено

```bash
openspec init --tools github-copilot        # → openspec/, .github/prompts/, .github/skills/
openspec new change add-pricing-discount-engine
# заповнення 4 артефактів у порядку, який диктує схема
openspec validate add-pricing-discount-engine --strict   # → valid
openspec status --change add-pricing-discount-engine     # → 4/4, 24 tasks
```

## 3. Що інструмент згенерував / що в репо

| Шлях | Ким створено | Що це |
|---|---|---|
| `openspec/config.yaml` | CLI (скелет), я (`context`, `rules`) | Схема + проєктний контекст, який підмішується в кожну інструкцію |
| `openspec/changes/add-pricing-discount-engine/.openspec.yaml` | CLI | Метадані зміни (схема, дата) |
| `.../proposal.md` | я, за шаблоном CLI | Навіщо, що змінюється, які capability, вплив |
| `.../specs/pricing/discounts/spec.md` | я, за шаблоном CLI | **Delta-спека**: 12 вимог SHALL/MUST, 20 сценаріїв WHEN/THEN |
| `.../design.md` | я, за шаблоном CLI | 10 рішень про **форму коду** (D-A…D-J) + таблиця ризиків |
| `.../tasks.md` | я, за шаблоном CLI | 24 задачі в 5 групах, кожна з файлом і AC-ID |
| `.github/prompts/opsx-*.prompt.md` (6) | CLI | Слеш-команди для Copilot: propose / apply / archive / explore / sync / update |
| `.github/skills/openspec-*/SKILL.md` (6) | CLI | Скіли, що вчать агента працювати з цим воркфлоу |

Стан: `openspec list` → `add-pricing-discount-engine  0/24 tasks`.
Реалізація (Task C) закриватиме ці чекбокси, далі `openspec archive` вливає
delta-спеку в `openspec/specs/` як діючий контракт.

## 4. Що він дав **понад** звичайну markdown-специфікацію

Чотири речі, яких у моєму `docs/spec/pricing-discounts.md` не було й не могло бути.

### 4.1 Виконуваний контроль повноти

`openspec status` — це не декоративний чекліст, а граф залежностей:

```
[x] proposal
[x] specs      (blocked by: proposal)
[x] design     (blocked by: proposal)
[ ] tasks      (blocked by: specs, design)
```

Поки немає specs і design, `tasks` фізично позначений заблокованим. Markdown-файл
такого не вміє: у ньому можна написати задачі першими й самому цього не помітити.

### 4.2 Валідатор, який ловить структурні дефекти

`openspec validate --strict` перевіряє реальні речі: кожна вимога має ≥1 сценарій;
сценарій із трьома `###` замість чотирьох **мовчки не парситься** (CLI явно
попереджає про цю пастку); `Purpose` коротший за 50 символів — помилка; зміна без
жодної delta відхиляється, якщо не позначена `skip_specs: true`. Це слабший
контроль, ніж тести, але сильніший за вичитування очима — і він запускається в CI.

### 4.3 Проєктні інваріанти, впорснуті в кожну інструкцію

Найцінніша частина. У `openspec/config.yaml` я записав `context` і `rules`:

```yaml
rules:
  specs:
    - Every requirement must cite the D-N decision(s) it encodes.
    - Every scenario must cite the AC-N id and use concrete kopeck amounts, never "correct".
  tasks:
    - Every task must name the file it touches and the AC ids it satisfies.
    - No task may modify app/src/pricing.ts or app/src/types.ts.
```

`openspec instructions specs` віддає це разом із завданням — у секціях
`<project_context>` і `<rules>`. Тобто «не чіпай `pricing.ts`» і «суми в копійках»
не треба повторювати в кожному промпті: вони прилітають агенту автоматично на
кожному артефакті. Це головна різниця з markdown-спекою — та є **пасивною**,
її треба не забути прочитати; конфіг OpenSpec **активно доставляється**.

### 4.4 Форсований етап design — і саме він знайшов дефект

Мій документ з Task A закривав *продуктові* розвилки. Схема `spec-driven` вимагає
окремо `design.md` — рішення про **форму коду**, з обов'язковою секцією
«Risks / Trade-offs». Заповнюючи її, я знайшов дві діри, які продуктова спека
не могла побачити:

| Знахідка | Наслідок, якби не знайшли | Куди пішло |
|---|---|---|
| `Date.parse("not-a-date")` → `NaN`, а будь-яке порівняння з `NaN` хибне → промокод із зіпсованою датою **тихо читався б як прострочений** | Дефект даних у каталозі маскується під нормальний стан «акція скінчилась» і не видно в метриках | Нове рішення **D-21** + **AC-21** у спеці, нова вимога у delta-спеці |
| Два записи з однаковим `code` у каталозі — не сказано, який виграє | Реалізація через `find` і через `Map` дають різний результат на тих самих даних — тобто неперевірюваний результат | Нове рішення **D-22** + **AC-22** |

Це буквально те, заради чого метод існує: етап знайшов розбіжність **до** написання
коду. Причому CLI прямо каже це робити — інструкція до `tasks` починається з
«check design.md for Open Questions … do not bake an unstated assumption into the
task list». Я їх закрив у спеці, а не в коді.

## 5. Що інструмент **не** зробив

Чесно, і це важливіше за список плюсів:

- **Не ухвалив жодного рішення.** Усі D-1…D-22 — мої. Порожній шаблон
  `## Decisions` з коментарем `<!-- Key design decisions with rationale -->` не
  думає замість людини. Дефект з `NaN` знайшов **я, коли заповнював його
  таблицю ризиків** — інструмент дав привід подивитись, не саму знахідку.
- **Не перевірив зміст, лише форму.** `validate --strict` каже «valid» і на
  специфікації, де AC-3 суперечить AC-7 — арифметику я звіряв руками. Гірше:
  я написав у `tasks.md` «тести через `node:test` + `tsx`», хоча в репо
  **vitest** — валідатор пропустив це без звуку, бо структура була коректна.
  Спіймав це `npm test`, а не інструмент. Артефакт, який не запускається,
  бреше так само впевнено, як і правдивий.
- **Не звʼязав себе з моєю спекою.** Посилання на `docs/spec/pricing-discounts.md`
  і цитування D-N/AC-N я вписав сам; ніщо не гарантує, що при правці одного
  документа другий оновиться. Дві копії правди — реальна ціна цього кроку.
- **Не згенерував тести й код.** `tasks.md` — це план для агента, не артефакт
  збірки.
- **Наплодив 12 файлів у `.github/`** під конкретного асистента. Для домашки —
  шум; у справжньому репо це треба свідомо вирішити комітити чи ні.
- **Мова.** Артефакти англійською (валідатор чекає `WHEN`/`THEN`), а спека —
  українською. Виник шар перекладу, якого без інструмента не було б.

## 6. Висновок

Для фічі такого розміру OpenSpec **не замінив** роботу з Task A і не скоротив її —
приблизно 40 хвилин зверху. Але він окупився двома конкретними речами:
`config.yaml` перетворив «пам'ятай про копійки й не чіпай `pricing.ts`» з наміру
на механізм, а обовʼязковий `design.md` витягнув баг `NaN`, який інакше знайшовся
б у проді як «чому знижка не працює». Одна ця знахідка — уже виправдання етапу.

Якби спека була гірша, інструмент цього б не врятував: він структурує мислення,
а не постачає його.
