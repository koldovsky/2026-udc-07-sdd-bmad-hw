# Task B — SDD-інструмент: OpenSpec

**Інструмент:** OpenSpec, версія **1.12.0** (`@fission-ai/openspec`)
**Схема робочого процесу:** `spec-driven` (proposal → specs → design → tasks)
**Вхід:** `docs/spec/pricing-discounts.md` (Task A)
**Команда ініціалізації:** `openspec init --tools claude --language uk`

Вибір: репозиторій на TypeScript, Node уже стоїть, OpenSpec — Node CLI без
додаткових рантаймів. Spec Kit і BMAD обидва потребують `uv`, якого тут не було.

перечитати з диска перед написанням.

## 2. Що він дав **понад** звичайну markdown-специфікацію

Чотири речі, і жодна з них не «згенерував текст».

**1. Примусово розділив ЩО і ЯК — і це змінило мій документ.**
Інструкція для артефакта `specs` містить прямий тест: «якщо реалізацію можна
змінити, не змінивши зовні видиму поведінку, це не належить специфікації», плюс
явна заборона на імена функцій і бібліотек. У моїй Task A-специфікації §3.1
(нормативний алгоритм) і §5 (сигнатура `priceOrder`) лежали поруч із критеріями
приймання. OpenSpec це рознесло: алгоритм, формула `percentOf`, вибір модуля
поїхали в `design.md`, а `specs/` лишився чистою поведінкою. Практичний
наслідок: delta-специфікацію тепер може відрев'ювати людина, яка не читає
TypeScript, — бізнес-власник кампанії, наприклад. Сам я цього розділення не
робив і, чесно кажучи, не збирався.

**2. Структурна валідація, якої в markdown немає в принципі.**
Це найконкретніше, що дає інструмент, тож я його перевірив, а не повірив на
слово. Три експерименти на власній специфікації:

| Експеримент | Результат |
|---|---|
| Requirement без жодного scenario | ✗ `ERROR: ADDED "..." must include at least one scenario` |
| Scenario з `###` замість `####` | ✗ `INFO` про проігнорований заголовок **+** `ERROR` на requirement, що лишився без сценаріїв |
| **AC-2 із неправильною арифметикою** (85 650 → 84 900) | ✓ `Change is valid` |

Перші два — реальна користь: «вимога без критерію приймання» це саме той дефект,
який markdown-файл проковтне мовчки, а рев'ювер пропустить. Третій — межа
інструмента, див. §3.

Побічно: скіл `openspec-propose` стверджує, що `###` замість `####` «fail
silently». У CLI 1.12.0 це неправда — помилка видається. **Документація
інструмента відстає від його ж поведінки**, рівно як попереджав walkthrough про
BMAD. Перевіряти треба CLI, а не текст навколо нього.

**3. Життєвий цикл специфікації, якого плоский файл не має.**
`specs/` усередині зміни — це **дельта** (`## ADDED / MODIFIED / REMOVED
Requirements`), а не копія специфікації. На `openspec archive` вона зіллється в
`openspec/specs/order-discounts/spec.md` — живий документ. Мій
`docs/spec/pricing-discounts.md` такого механізму не має: щойно зʼявиться друга
фіча зі знижками, він почне розходитися з кодом, і ніщо про це не повідомить.
Ось тут інструмент виграє не на цій задачі, а на п'ятій.

**4. Розбиття на задачі як дані, а не як текст.**
`tasks.md` парситься: `openspec list` показує `0/22 tasks`. Інструкція вимагала,
щоб **кожна** задача містила спосіб перевірки. Це змусило мене писати не
«реалізувати вибір купона», а «перевірка — тест `AC-3` дає `not_best` для
фіксованого промокоду». Task A такого розбиття не мала взагалі — я б пішов
писати код одразу.

## 3. Чого він не дав і що довелося робити руками

**Він не ухвалив жодного рішення.** Це головне. Усі 16 розвилок (D-1…D-16) —
результат Task A. OpenSpec жодного разу не спитав «складати відсотки чи
застосовувати послідовно?» і однаково спокійно прийняв би будь-яку відповідь.
Експеримент 3 вище це доводить: `--strict` пропустив AC-2 зі значенням 84 900 —
тобто **саме той адитивний баг, заради запобігання якому вся специфікація й
писалася**. Валідація структурна, не семантична. Інструмент перевіряє, що
критерій приймання існує; чи він правильний — не його справа.

Решта ручної роботи:

- **Усі числа мої.** 85 650 проти 84 900, 959 проти 960, межа
  `2026-10-01T00:00:00.000Z` — пораховано в Task A. Шаблон дав рамку `WHEN/THEN`,
  не зміст.
- **Дублювання контенту.** Тепер рішення живуть у двох місцях:
  `docs/spec/pricing-discounts.md` (з колонкою «чому») і `openspec/.../spec.md`
  (без неї, бо специфікація не місце для обґрунтувань). Це реальна ціна: два
  документи розійдуться, якщо не домовитись, який головний. Домовляюсь:
  **Task A-документ — джерело рішень і обґрунтувань, OpenSpec-дельта — джерело
  вимог до поведінки.**
- **`.claude/*` був у `.gitignore`** — 12 файлів, які згенерував `openspec init`,
  мовчки не потрапили б у PR. Довелося дописати два винятки в `.gitignore`.
  Інструмент про це не попереджає.
- **`--language uk` — це підказка мені, а не примус.** Рядок «All artifacts must
  be written in uk» просто приїжджає в поле `context` кожної інструкції. Якби
  агент його зігнорував, ніщо б не спрацювало.
- **Телеметрія ввімкнена за замовчуванням** — вимкнув
  (`openspec config set telemetry.enabled false`).
- **Версія 1.12.0 відрізняється від того, що описано в статтях.** Робочий процес
  тепер `opsx:*` зі скілами; орієнтуватись треба на `openspec --help`.

## 4. Висновок: навіщо він тут

Для **цієї** задачі — одна функція, один модуль — OpenSpec окупився частково.
Дві речі я не отримав би без нього: розділення поведінки й реалізації
(§2.1) і машинну перевірку «кожна вимога має критерій приймання» (§2.2). Обидві
реальні, обидві покращили артефакти. Решта — 22 задачі, дельта-формат — на
масштабі однієї фічі радше акуратність, ніж виграш.

Де він справді окупиться — видно з механізму, а не з цього прогону:
`openspec/specs/` як **живий** набір специфікацій, у який дельти зливаються при
архівації. На третій-п'ятій фічі це різниця між «специфікації є» і «специфікації
відповідають коду».

Чого від нього чекати не варто: він **не думає за вас**. Найдорожча частина
роботи — знайти неоднозначності в тікеті й свідомо їх закрити — цілком лишилась
у Task A. OpenSpec дав цим рішенням структуру, перевірювану форму й місце, де
вони переживуть наступну фічу. Але якби я прийшов до нього з переказом тікета
замість специфікації, він би слухняно згенерував валідну структуру навколо
невирішених питань — і `validate --strict` сказав би `valid`.

**Час:** ~23 хв (встановлення 1, вивчення CLI 4, написання 4 артефактів 15,
експерименти з валідатором 3).

## Як відтворити

```bash
npm install -g @fission-ai/openspec@latest
openspec init --tools claude --language uk
openspec new change "add-order-discounts"
openspec status --change add-order-discounts --json     # порядок артефактів
openspec instructions proposal --change add-order-discounts --json
# ... proposal → specs → design → tasks
openspec validate add-order-discounts --strict
openspec list
```
