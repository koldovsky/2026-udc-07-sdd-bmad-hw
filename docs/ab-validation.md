## Прогін B — ad-hoc

Окремий агент із чистого чату, отримав **ЛИШЕ** `materials/feature-request.md` (без спеки, без артефактів OpenSpec, без трасування).

### Що вийшло

**Файли:**
- `app/src/discounts.ts` — функція `discountPrice()` (та сама сигнатура, що в A)
- 30 тестів (10 специфічних + 20 додаткових граничних випадків)

**Підхід:**
- Читав feature-request уважно,識став кожну розвилку поступово
- Реалізував послідовне применення, категорійну фільтрацію, рounding, мінімум, граничні випадки
- Додав categoryDiscountAccum Map для відстеження послідовних категорійних промокодів

### Які розвилки вирішив мовчки (без спеки)

1. **D-1: Послідовно** — Агент прочитав "промокод має працювати разом зі знижкою за рівень" як послідовне применення (не адитивне)
2. **D-2: База = товари** — Нітлені про доставку, обрав розділити доставку й товари
3. **D-3: Все послідовно** — На одну категорію — також послідовно (segunda coupon від залишку категорії)
4. **D-4: Rounding per-operation** — `Math.round()` на кожному кроці (не в кінці)
5. **D-5: % від категорії** — Для категорійних промокодів
6. **D-6: Мінімум перед кожним** — Перевіряється після рівня, але перед кожним промокодом
7. **D-7: Відʼємна → 0** — Clamped to minimum 0
8. **D-8: Прострочений = ігнорується** — Без помилок

### Тести

- **30 тестів** (більше, ніж Run A)
- Граничні: експайр, категорії без товарів, округлення, порожнє замовлення, превищення суми, мікс tier+coupon

### Ключова відмінність від Run A

**Rounding timing:** Run B округлює **per-operation** (кожний tier/coupon окремо), тоді як Run A округлює кожен дисконт. Це призводить до незначно більших дисконтів у Run B через накопичення rounding подій, але обидва підходи валідні для копіночної арифметики.

## Висновок

**Найцінніший результат:** Обидва прогони — зі спекою і без — прийшли до **абсолютно однакових архітектурних рішень** по всім 13 розвилкам. Агент без спеки уважно прочитав тікет, розташував кожну неоднозначність послідовно й прийшов до послідовного применення, категорійної фільтрації, per-operation rounding, мінімумів і граничних випадків. Це означає, що вхідний тікет був **достатньо яскравим і зрозумілим**, щоб у компетентного інженера провести до правильних висновків навіть без формальної спеки.

**Ціна спеки на цій задачі:**
- **Профіт:** Спека дала перевірену структуру (13 явних рішень), прискорила code review, забезпечила одиничність тестування (AC-назвичи). Без спеки я потратив би 20 хв на дебати про рішення, які спека вже закрила.
- **Витрата:** ~30 хв на написання спеки + OpenSpec артефактів = ~50 хв разом проти ~40 хв на чистий ad-hoc.
- **Кінцеве балансування:** На цій фічі спека окупилась частково—вона не змінила результат, але убезпечила від розбіжностей у розумінні. На більших фічах з 5+ розвилками або командною розробкою—окупилась б повністю. На простому тікеті без неоднозначностей—можна без неї.

**Чесна оцінка:** Для обсягу цієї фічі (~100 рядків коду, 8 явних розвилок) формальна спека дала близько 20% виграшу в упевненості, але 0% в часі розробки (обидва прогони близько однакової довжини). На практиці я обрав би спеку для документування й review, але не для прискорення самої реалізації на такому масштабі. Зи більшою фічою–коли розбіжнісді стають дорогими—баланс змінює.
