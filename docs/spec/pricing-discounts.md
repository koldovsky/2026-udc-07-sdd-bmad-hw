# Специфікація: знижки при оформленні замовлення

**Статус:** agreed
**Джерело:** `materials/feature-request.md`
**Автор рішень:** slava5879
**Дата:** 2026-09-07

---

## 1. Мета

Після релізу сума до сплати за будь-яке замовлення обчислюється однією чистою
функцією, яка враховує рівень лояльності та промокоди й повертає розкладку, а не
лише підсумок: скільки дав рівень, скільки дав промокод, який промокод
застосувався і чому решта — ні.

Головна вимога — **детермінованість**: два різні інженери (або два прогони
агента) за цим документом отримають однакову поведінку до копійки. Тому кожна
розвилка з тікета закрита рішенням у §3, а порядок операцій зафіксований
нормативним алгоритмом у §3.1.

## 2. Поза скоупом

Свідомо **не** робимо в цій ітерації:

- **Валідація каталогу купонів.** `Coupon` вважається коректним: `percent` у
  межах 0–100, `fixed` ≥ 0, `expiresAt` — валідний ISO-інстант. Некоректні дані
  каталогу — це помилка виклику, а не правило ціноутворення. Гілок коду під це
  немає, тестів теж.
- **Нормалізація коду** (trim, upper-case, розкладка клавіатури). Зіставлення
  точне (D-13); нормалізація — задача UI чекауту.
- **Знижка на доставку та безкоштовна доставка.** Доставка ніколи не
  дисконтується (D-2), купонів типу «free shipping» не існує.
- **Ліміти використання**: одноразові коди, ліміт на клієнта, бюджет кампанії,
  видача та генерація кодів. У типі `Coupon` немає даних для цього.
- **Податки, ПДВ, валюти крім гривні, повернення й часткові повернення.**
- **Тексти для користувача.** `rejectedCoupons` повертає машинні коди причин;
  переклад і формулювання — на боці UI.
- **Зміни `app/src/pricing.ts` і `app/src/types.ts`** — це засіяний контракт.

Підсумок ≥ 0. | Відʼємний підсумок — це виплата клієнту, а не знижка; жодне з правил тікета такого не обіцяло. Доставка не обнуляється разом із товарами, бо витрата на перевізника лишається реальною навіть тоді, коли товар віддано безкоштовно (D-2). Обмеження знизу гарантує, що система ніколи не згенерує кредит через комбінацію правил. | AC-4 |

### 3.1 Алгоритм (нормативний)

Порядок операцій обовʼязковий: він і є тим, що робить D-1, D-4, D-5 та D-7
однозначними. Усі величини — цілі копійки.

```text
roundHalfUp(база, відсоток) = ⌊(база × відсоток + 50) / 100⌋

 1. subtotal    = subtotalKopecks(order)                       // з pricing.ts
 2. tierPct     = tierPercent(order)                           // з pricing.ts
 3. tierDiscount = roundHalfUp(subtotal, tierPct)
 4. afterTier   = subtotal − tierDiscount

 5. Кандидати: order.coupons → дедуплікація зі збереженням порядку (D-12)
                             → пошук у каталозі, точне зіставлення (D-13)
 6. Придатність кожного кандидата, перша спрацьована причина перемагає (D-14):
      немає в каталозі                             → unknown
      now >= Date(expiresAt)                       → expired            (D-11)
      minSubtotalKopecks задано і subtotal < нього → min_subtotal_not_met (D-6)
      category задано і в замовленні немає таких рядків → category_absent (D-10)

 7. Для кожного придатного кандидата:
      base = category задано
               ? categoryTotal − roundHalfUp(categoryTotal, tierPct)    (D-5)
               : afterTier
        де categoryTotal = сума lineTotalKopecks рядків цієї категорії
      discount = kind === "percent" ? roundHalfUp(base, value)
                                    : min(value, base)                  (D-5)

 8. Кандидати зі знижкою 0 відпадають → no_effect                        (D-16)
    Переможець = найбільший discount серед решти; при рівності — найраніший
    у порядку введення (D-3). Решта придатних → not_best.
 9. couponDiscount = min(discount(переможця), afterTier)     // 0, якщо переможця немає
10. goodsTotal     = afterTier − couponDiscount              // ≥ 0 за побудовою (D-7)
11. total          = goodsTotal + shippingKopecks(order)     // доставка поза знижками (D-2)
```

## 4. Критерії приймання

Формат: `AC-N: КОЛИ <ситуація>, ТОДІ <очікувана поведінка>`. Усі суми — у
копійках, у дужках — гривні для читабельності. Стандартний товар — категорія
`standard`, країна `UA` (доставка 4 900 = 49 грн), якщо не сказано інше.
`now` = `2026-09-07T12:00:00.000Z`, якщо не сказано інше.

**Рівень лояльності та база знижки**

- **AC-1:** КОЛИ замовлення на 100 000 (1 000 грн) від Gold-клієнта без
  промокодів, ТОДІ `tierDiscountKopecks` = 10 000 (100 грн),
  `couponDiscountKopecks` = 0, `shippingKopecks` = 4 900,
  `totalKopecks` = **94 900** (949 грн) — доставка не дисконтується.

- **AC-2:** КОЛИ замовлення на 100 000 (1 000 грн) від Silver-клієнта з
  промокодом `PROMO15` (percent 15, без обмежень), ТОДІ рівень дає 5 000,
  промокод рахується від залишку 95 000 і дає 14 250 (142,50 грн),
  `totalKopecks` = **85 650** (856,50 грн) — а не 84 900, як дало б адитивне
  складання 5% + 15%.

**Кілька промокодів**

- **AC-3:** КОЛИ замовлення містить 60 000 у категорії `fresh` і 40 000 у
  `standard`, рівень `none`, а клієнт увів `FRESH10` (percent 10, category
  fresh) і `FRESH50` (fixed 5 000, category fresh), ТОДІ застосовується лише
  `FRESH10` зі знижкою 6 000 (60 грн), `appliedCouponCode` = `"FRESH10"`,
  `FRESH50` потрапляє в `rejectedCoupons` з причиною `not_best`,
  `totalKopecks` = **98 900** (989 грн).

- **AC-15:** КОЛИ той самий код `PROMO15` введено двічі
  (`coupons: ["PROMO15", "PROMO15"]`) на замовленні 100 000 без рівня, ТОДІ
  знижка нараховується один раз — 15 000, `rejectedCoupons` порожній,
  `totalKopecks` = **89 900** (899 грн).

**Термін дії**

- **AC-5:** КОЛИ промокод `OLD15` має `expiresAt` = `2026-09-01T00:00:00.000Z`,
  а `now` = `2026-09-07T12:00:00.000Z`, ТОДІ функція **не кидає виняток**,
  `couponDiscountKopecks` = 0, `appliedCouponCode` = `null`,
  `rejectedCoupons` = `[{ code: "OLD15", reason: "expired" }]`,
  `totalKopecks` = **104 900** (1 049 грн).

- **AC-6 (граничний):** КОЛИ `expiresAt` = `2026-10-01T00:00:00.000Z`, ТОДІ при
  `now` = `2026-09-30T23:59:59.999Z` купон застосовується, а при
  `now` = `2026-10-01T00:00:00.000Z` (рівно момент закінчення) — відхиляється з
  причиною `expired`.

**Мінімальна сума**

- **AC-7 (граничний):** КОЛИ замовлення на рівно 50 000 (500 грн) від
  Gold-клієнта з купоном `MIN500` (percent 10, `minSubtotalKopecks` 50 000),
  ТОДІ поріг вважається досягнутим (перевірка проти сирої суми 50 000, а не
  проти 45 000 після знижки за рівень), знижка за рівень 5 000, знижка за
  купоном 4 500, `totalKopecks` = **45 400** (454 грн).

- **AC-8:** КОЛИ замовлення на 49 999 (499,99 грн) з тим самим `MIN500`, ТОДІ
  купон відхиляється з причиною `min_subtotal_not_met`,
  `couponDiscountKopecks` = 0, `totalKopecks` = **54 899**.

**Категорійні промокоди**

- **AC-11:** КОЛИ замовлення містить 30 000 у категорії `digital` і 70 000 у
  `standard`, рівень `none`, купон `DIGI20` (percent 20, category digital),
  ТОДІ знижка = 6 000 (20% від 30 000), а **не** 20 000,
  `totalKopecks` = **98 900** (989 грн).

- **AC-12:** КОЛИ в замовленні лише `standard`-товари на 100 000, а введено
  `FRESH10` (category fresh), ТОДІ купон відхиляється з причиною
  `category_absent`, `appliedCouponCode` = `null`, `totalKopecks` = **104 900**.

- **AC-14:** КОЛИ Gold-клієнт замовляє 60 000 у `fresh` і 40 000 у `standard`
  з купоном `FRESH10` (percent 10, category fresh), ТОДІ база купона — сума
  категорії після знижки за рівень: 60 000 − 6 000 = 54 000, знижка за купоном
  5 400, знижка за рівнем на все замовлення 10 000,
  `totalKopecks` = **89 500** (895 грн).

**Невідомий код**

- **AC-13:** КОЛИ введено код `NOPE`, якого немає в каталозі, на замовленні
  100 000 без рівня, ТОДІ `rejectedCoupons` = `[{ code: "NOPE", reason: "unknown" }]`,
  знижок немає, `totalKopecks` = **104 900**.

**Граничні випадки**

- **AC-4 (граничний):** КОЛИ замовлення на 10 000 (100 грн), рівень `none`, а
  купон `SUPER` дає фіксовані 20 000 (200 грн), ТОДІ знижка обмежується сумою
  товарів — `couponDiscountKopecks` = 10 000, товарна частина = 0, підсумок **не
  відʼємний**, доставка сплачується: `totalKopecks` = **4 900** (49 грн).

- **AC-9 (граничний, пів копійки):** КОЛИ Silver-клієнт замовляє один
  `digital`-товар за 1 010 (10,10 грн) без промокодів, ТОДІ знижка за рівнем =
  5% від 1 010 = 50,5 копійки, що округлюється **вгору** до 51,
  `shippingKopecks` = 0 (усе цифрове), `totalKopecks` = **959** (9,59 грн) —
  а не 960, як дало б округлення вниз чи «до парного».

- **AC-10 (граничний):** КОЛИ замовлення порожнє (`items: []`) з будь-яким
  рівнем і будь-якими кодами, ТОДІ функція не кидає виняток,
  `subtotalKopecks` = 0, обидві знижки = 0, `shippingKopecks` = 0,
  `totalKopecks` = **0**.

- **AC-16 (граничний, нульовий ефект):** КОЛИ замовлення містить рядок `fresh`
  на 10 копійок і рядок `standard` на 100 000, рівень `none`, а купон `TINY1`
  (percent 1, category fresh) дає 1% від 10 = 0,1 копійки → 0 після округлення,
  ТОДІ купон **не** застосовується: `appliedCouponCode` = `null`,
  `rejectedCoupons` = `[{ code: "TINY1", reason: "no_effect" }]`,
  `totalKopecks` = **104 910**.

> Разом 16 критеріїв, з них 6 граничних (AC-4, AC-6, AC-7, AC-9, AC-10, AC-16).

## 5. Контракт

Нове в `app/src/discounts.ts`. Типи `Order`, `Coupon`, `LineItem` беруться з
`app/src/types.ts` без змін; `subtotalKopecks`, `lineTotalKopecks`,
`shippingKopecks`, `tierPercent` — з `app/src/pricing.ts` без змін.

```ts
import type { Order, Coupon } from "./types.js";

/** Чому купон не спрацював. Порядок відповідає пріоритету з D-14. */
export type CouponRejectionReason =
  | "unknown"
  | "expired"
  | "min_subtotal_not_met"
  | "category_absent"
  | "no_effect"
  | "not_best";

export interface RejectedCoupon {
  code: string;
  reason: CouponRejectionReason;
}

export interface PriceBreakdown {
  /** Сума товарів до знижок. */
  subtotalKopecks: number;
  /** Знижка за рівнем лояльності. */
  tierDiscountKopecks: number;
  /** Знижка за промокодом-переможцем; 0, якщо жоден не застосовано. */
  couponDiscountKopecks: number;
  /** Код промокоду, що спрацював, або null. */
  appliedCouponCode: string | null;
  /** Усі введені коди, що не спрацювали, з причиною (по одній, D-14). */
  rejectedCoupons: RejectedCoupon[];
  /** Доставка — не дисконтується (D-2). */
  shippingKopecks: number;
  /** До сплати. Завжди ≥ 0 (D-7). */
  totalKopecks: number;
}

/**
 * Чиста функція: без Date.now(), без вводу-виводу, без винятків.
 * @param catalogue усі відомі купони; зіставлення за `code`, точне (D-13)
 * @param now момент оцінки терміну дії (D-11)
 */
export function priceOrder(
  order: Order,
  catalogue: Coupon[],
  now: Date,
): PriceBreakdown;
```

Інваріанти, що мають виконуватись для будь-якого входу:

- `totalKopecks === subtotalKopecks − tierDiscountKopecks − couponDiscountKopecks + shippingKopecks`
- `tierDiscountKopecks + couponDiscountKopecks <= subtotalKopecks`
- `totalKopecks >= 0`
- усі поля — цілі числа
- `appliedCouponCode !== null` ⟺ `couponDiscountKopecks > 0` (D-16)
- `rejectedCoupons.length` + (`appliedCouponCode` ? 1 : 0) = кількість
  **унікальних** кодів у `order.coupons` (D-12) — жоден введений код не зникає
  з розкладки безслідно

## 6. Як перевірити

```bash
cd app && npm test
```

Очікується: 8 засіяних тестів + по одному тесту на кожен критерій із §4,
названому за його ID (`AC-3: два промокоди на одну категорію`), — тож звʼязок
зі специфікацією видно прямо у виводі vitest. Плюс:

```bash
cd app && npm run typecheck
```

Специфікація вважається виконаною, коли кожен AC із §4 має рядок у
`docs/traceability.md` із посиланням на реальний код і реальний тест, а
зворотна перевірка не знайшла ані поведінки без AC, ані AC без тесту.
