# Специфікація: Рушій знижок на checkout (рівні лояльності + промокоди)

**Статус:** agreed
**Джерело:** `materials/feature-request.md`
**Автор рішень:** Sergii Osadchyi
**Версія:** 1.0

---

## 1. Мета

Після релізу підсумкова сума замовлення на checkout має враховувати знижку за
рівнем лояльності та введені клієнтом промокоди — детерміновано, у цілих
копійках і з поясненням, які промокоди спрацювали, а які ні й чому.

Головна вимога — **відтворюваність**: на одному й тому самому замовленні,
наборі промокодів і моменті часу розрахунок завжди дає той самий результат,
незалежно від реалізації.

## 2. Поза скоупом

Свідомо **не** робимо в цій ітерації:

- зміну сигнатур/поведінки `subtotalKopecks`, `lineTotalKopecks`,
  `shippingKopecks`, `tierPercent` — вони стабільні;
- знижки на доставку (промокоди «безкоштовна доставка»), безкоштовні товари,
  подарунки, бандли, «2+1»;
- податки, ПДВ, мультивалютність, конвертацію валют;
- ліміт використань промокоду (`usageLimit`), персональні/одноразові коди,
  прив'язку промокоду до клієнта — у `Coupon` таких полів немає;
- дату **початку** дії промокоду — у `Coupon` є лише `expiresAt`;
- персистентність, БД, HTTP-шар, UI-тексти помилок (специфікуємо коди причин,
  не формулювання);
- будь-яке округлення до «гарних» чисел, приховані мінімальні суми до сплати,
  кешбек, бали.

> Усе, що не описане в розділах 3–5, реалізовувати **не можна**. Якщо агент
> «допоміг» і додав поведінку, якої не просив жоден AC, — це дефект (зворотна
> перевірка в Task C).

## 3. Рішення щодо неоднозначностей

Наскрізні терміни, які вживаються нижче:

- **Товарна база (`subtotal`)** — `subtotalKopecks(order)`, сума позицій без доставки.
- **Залишок (`remaining`)** — поточна сума товарів після вже застосованих знижок.
  Стартує рівним `subtotal` і монотонно не зростає.
- **Момент розрахунку (`now`)** — явний параметр; за замовчуванням поточний час.

| # | Питання | Рішення | Чому саме так |
|---|---|---|---|
| D-1 | Промокод і рівень складаються чи застосовуються послідовно? | **Послідовно, рівень першим**: спершу знижка за рівнем від `subtotal`, потім промокоди від `remaining`. 10% + 15% на 100 000 коп. = 10 000 + 13 500 = 23 500 коп., а не 25 000. | Сумарна знижка ніколи не перевищить очікувану й ніколи не досягне 100% від додавання кількох відсотків. Рівень — властивість клієнта (стабільна), промокод — разова акція поверх неї; такий порядок дає передбачувану верхню межу маркетингових витрат. |
| D-2 | База знижки — товари чи товари + доставка? | **Тільки товари.** Доставка (`shippingKopecks`) ніколи не дисконтується і додається до підсумку **після** всіх знижок. | Доставка — це собівартість перевізника, а не маржа. Дисконт на неї — окремий продукт («безкоштовна доставка»), якого в тікеті немає (див. «Поза скоупом»). |
| D-3 | Кілька промокодів — усі / найвигідніший / перший? | **Усі валідні, послідовно, у порядку введення** (`order.coupons`), але **не більше одного промокоду на один скоуп**. Скоуп = `category` промокоду або `"ORDER"` для промокоду без категорії. Другий і наступні промокоди того самого скоупу відхиляються з причиною `duplicate_scope`. | «Усі» — бо тікет каже «клієнт має відчувати вигоду»; порядок введення — бо він єдиний детермінований сигнал, який ми маємо (`coupons` описані як «in the order they typed them»), і його не треба пояснювати клієнту. Обмеження «один на скоуп» закриває найдорожчу дірку — стекінг кодів на одну категорію. |
| D-4 | Округлення: де і в який бік? | Усі суми — **цілі копійки**. Округлення виконується **на кожному кроці знижки** (не по рядках і не лише в кінці) за правилом **half-up від нуля**: `floor(x + 0.5)`. Пів копійки → вгору (202.5 → 203). Проміжні значення не зберігаються дробовими. | Крокове округлення робить кожен рядок breakdown цілим числом, тож `subtotal − усі знижки + доставка === total` виконується тотожно й «копійки не пливуть». Half-up — банківський дефолт, зрозумілий і бухгалтерії, і клієнту; ~0.5 коп. на крок — прийнятна ціна за просте, ручно-перевірюване правило. |
| D-5 | Промокод на категорію рахується від чого? | Від **частки цієї категорії в поточному залишку**: `categoryBase = round(categorySubtotal × remaining / subtotal)`, знижка = `round(categoryBase × percent / 100)`. Для `fixed` — знижка = `min(value, categoryBase)`. Якщо `subtotal === 0`, то `categoryBase = 0`. | Рахувати від усього замовлення — обман клієнта; рахувати від повної суми категорії ігноруючи вже надану знижку за рівнем — подвійний дисконт на ті самі гроші. Пропорційна частка залишку — єдиний варіант, що зберігає інваріант «сума знижок ≤ subtotal» і не залежить від порядку категорій. |
| D-6 | `minSubtotalKopecks` перевіряється до чи після інших знижок? | **До всіх знижок**, проти початкового `subtotal`. Умова: `subtotal >= minSubtotalKopecks`. Інакше — відхилення з причиною `below_min_subtotal`. | Клієнт бачить поріг у кошику ще до розрахунку («до 1 000 грн — знижка»); перевірка після знижок робила б результат залежним від порядку промокодів і породжувала б «зникаючі» знижки. Поріг — інклюзивний (`>=`), бо «від 1 000 грн» у маркетингу означає «1 000 включно». |
| D-7 | Чи може підсумок стати відʼємним? | **Ні.** Кожна знижка обрізається до поточного `remaining`; `remaining >= 0` завжди. Нижня межа товарної частини — 0 коп. `total = remaining + shipping`, тобто мінімальний підсумок = вартість доставки. Знижка ніколи не переходить у доставку і не повертає гроші. | Відʼємний підсумок означав би виплату клієнту — це не знижка, а платіжна операція, якої система не вміє. Обрізання до залишку зберігає інваріант і робить поведінку на «завеликому» промокоді очевидною. |
| D-8 | Прострочений промокод — тиха відмова чи помилка? | **Не тиха й не виняток**: розрахунок успішно завершується, промокод потрапляє у `rejectedCoupons` з причиною `expired`. Функція **не кидає** винятків за жодних вхідних даних. | Виняток ламає весь checkout через один зайвий код у полі — неприйнятно. Тиха відмова породжує тікети в підтримку «де моя знижка». Структурована відмова дає UI змогу показати причину, а нам — метрику. |
| D-9 | Що таке «прострочений»? Як порівнюємо час? | Промокод недійсний **у момент `expiresAt` і після нього**: валідний, якщо `now < Date.parse(expiresAt)`. Порівняння в UTC. `now` — явний параметр контракту (за замовчуванням `new Date()`). | Дослівно з `types.ts`: «not valid on or after this instant». Явний `now` робить тести детермінованими — інакше AC на строк дії неможливо перевірити стабільно. |
| D-10 | Код, якого немає в каталозі промокодів | Відхиляється з причиною `unknown`. Розрахунок не переривається. | Одруківка клієнта не має ламати оплату; сигнатура `order.coupons: string[]` прямо допускає довільний текст. |
| D-11 | Один і той самий код введено двічі | Застосовується **один раз**; повторні входження відхиляються з причиною `duplicate_code` (перевіряється до `duplicate_scope`). | Очевидна помилка вводу, а не спроба стекінгу; окрема причина дає змогу відрізнити її в метриках від реального стекінгу по скоупу. |
| D-12 | Промокод на категорію, якої немає в замовленні | Відхиляється з причиною `no_matching_items` (не «застосований зі знижкою 0»). | Нульова знижка у списку застосованих виглядає як баг і забруднює breakdown; явна причина чесніша й тестується. |
| D-13 | Некоректні дані промокоду (`percent` поза 0–100, `value < 0`, `fixed` з `value = 0`) | Відхиляється з причиною `invalid_value`. Ніякого «підганяння» до меж. | Тихе кліпування 150% до 100% — це рішення про гроші, ухвалене кодом. Краще гучно відхилити невалідний запис каталогу. |
| D-14 | Порожнє замовлення (`items: []`) | `subtotal = 0`; `shippingKopecks(order)` за наявною логікою дає 0 (`every` на порожньому масиві → `true`); усі знижки 0; `total = 0`. Будь-який промокод отримує базу знижки 0 і відхиляється з причиною `no_matching_items` (або раніше — `below_min_subtotal`, якщо має поріг). Винятків не кидаємо. | Порожній кошик не має бути особливим кодом-шляхом: правила D-5/D-7 самі дають 0. Фіксуємо явно, щоб ніхто не «додав» перевірку, яка кидає помилку, і щоб у `appliedCoupons` не зʼявився запис зі знижкою 0. |
| D-15 | Що з рівнем `none` | `tierPercent = 0` → `tierDiscountKopecks = 0`; промокоди рахуються від повного `subtotal`. Окремої гілки коду немає. | Рівень — просто відсоток; нуль не потребує спецобробки. |
| D-16 | Чи впливають знижки на доставку (в т.ч. на правило «все digital → 0») | Ні. `shippingKopecks(order)` викликається на **вихідному** замовленні й не залежить від жодної знижки. | Поведінка доставки вже специфікована й покрита 8 наявними тестами — ми її не чіпаємо. |
| D-17 | Порядок обробки одного промокоду | Для кожного коду по черзі: (1) `unknown` → (2) `duplicate_code` → (3) `invalid_value` → (4) `expired` → (5) `below_min_subtotal` → (6) `duplicate_scope` → (7) обчислення бази й знижки → (8) `no_matching_items`, якщо база = 0. Перша спрацьована перевірка визначає причину. | Без фіксованого порядку промокод із двома вадами дає різну причину в різних реалізаціях — тобто нетестований результат. |
| D-18 | Чи впливає порядок промокодів на суму | Так, і це прийнято свідомо: порядок = порядок введення (D-3). | Альтернатива «шукати найвигіднішу комбінацію» — це оптимізаційна задача, вона непередбачувана для клієнта й дорога; тікет її не просить. |
| D-19 | Що вважається сумою категорії | `categorySubtotal` = сума `lineTotalKopecks` по всіх позиціях із цією `category`. | Прибирає питання «а якщо кілька рядків однієї категорії». |
| D-20 | Чи є верхня межа сумарної знижки (напр. 50%) | **Немає**, окрім природної межі `remaining >= 0` (D-7). | Тікет її не просить; вигаданий кап — це неспецифікована поведінка. Якщо бізнес захоче — це нова версія специфікації, а не «здоровий глузд» у коді. |

## 4. Критерії приймання

Формат: `AC-N: КОЛИ <ситуація>, ТОДІ <очікувана поведінка>`.
Усі суми — копійки. Скорочення: `UA` — доставка 4 900; не-`UA` — 19 900.

- **AC-1 (рівень підключено):** КОЛИ замовлення `UA` на 100 000 коп. (`standard`)
  від `gold`-клієнта **без промокодів**, ТОДІ `tierDiscountKopecks = 10 000`,
  `couponDiscountKopecks = 0`, `shippingKopecks = 4 900`, `totalKopecks = 95 100`.

- **AC-2 (silver і none):** КОЛИ те саме замовлення на 100 000 коп. від
  `silver`-клієнта, ТОДІ `tierDiscountKopecks = 5 000`, `totalKopecks = 99 900`;
  КОЛИ від клієнта з `customerTier = "none"`, ТОДІ `tierDiscountKopecks = 0`,
  `totalKopecks = 104 900`.

- **AC-3 (складання = послідовне, D-1):** КОЛИ замовлення `UA` на 100 000 коп.
  від `gold` з промокодом `AUTUMN15` (`percent`, 15, без категорії, дійсний),
  ТОДІ `tierDiscountKopecks = 10 000`, `couponDiscountKopecks = 13 500`
  (15% від залишку 90 000, **не** 15 000), товари після знижок = 76 500,
  `totalKopecks = 81 400`.

- **AC-4 (база не включає доставку, D-2):** КОЛИ замовлення на 100 000 коп. від
  `gold` з `country = "PL"` (доставка 19 900) без промокодів, ТОДІ
  `tierDiscountKopecks = 10 000` (**не** 11 990) і `totalKopecks = 109 900`.

- **AC-5 (промокод на категорію, D-5):** КОЛИ замовлення `UA` містить
  `standard` на 60 000 і `fresh` на 40 000 (subtotal 100 000), клієнт `gold`,
  промокод `FRESH20` (`percent`, 20, `category: "fresh"`), ТОДІ
  `tierDiscountKopecks = 10 000`, база категорії = `40 000 × 90 000 / 100 000 = 36 000`,
  `couponDiscountKopecks = 7 200`, товари = 82 800, `totalKopecks = 87 700`.

- **AC-6 (два промокоди на одну категорію, D-3):** КОЛИ до замовлення з AC-5
  введено `["FRESH20", "FRESH10"]` (обидва `category: "fresh"`, дійсні), ТОДІ
  застосовується лише `FRESH20` (`couponDiscountKopecks = 7 200`), а `FRESH10`
  потрапляє у `rejectedCoupons` з причиною `duplicate_scope`;
  `totalKopecks = 87 700` (як в AC-5).

- **AC-7 (різні скоупи стекуються по порядку, D-3/D-18):** КОЛИ до замовлення з
  AC-5 введено `["FRESH20", "ORDER10"]` (`ORDER10` — `percent` 10 без категорії),
  ТОДІ знижки: рівень 10 000 → `FRESH20` 7 200 (залишок 82 800) → `ORDER10`
  8 280 (залишок 74 520), `couponDiscountKopecks = 15 480`,
  `totalKopecks = 79 420`.

- **AC-8 (мінімальна сума — до знижок, D-6):** КОЛИ замовлення на 100 000 коп.
  від `gold` (залишок після рівня — 90 000) з промокодом `MIN95K`
  (`fixed`, 5 000, `minSubtotalKopecks: 95 000`), ТОДІ промокод **застосовується**
  (перевірка проти вихідних 100 000), `couponDiscountKopecks = 5 000`,
  `totalKopecks = 89 900`.

- **AC-9 (поріг не досягнуто):** КОЛИ замовлення на 94 999 коп. із тим самим
  `MIN95K`, ТОДІ промокод у `rejectedCoupons` з причиною `below_min_subtotal`,
  `couponDiscountKopecks = 0`. КОЛИ subtotal рівно 95 000 — промокод
  застосовується (поріг інклюзивний).

- **AC-10 (прострочений промокод, D-8/D-9):** КОЛИ `now = 2026-10-01T00:00:00Z`
  і промокод `OLD10` має `expiresAt = "2026-10-01T00:00:00Z"`, ТОДІ він
  недійсний (`now < expiresAt` хибне): `rejectedCoupons` містить
  `{ code: "OLD10", reason: "expired" }`, `couponDiscountKopecks = 0`,
  функція **не кидає** винятку, решта розрахунку — як без промокоду.
  КОЛИ `now = 2026-09-30T23:59:59Z` — той самий промокод дійсний.

- **AC-11 (граничний — знижка більша за суму, D-7):** КОЛИ замовлення `UA` на
  5 000 коп. (`standard`) від клієнта `none` з промокодом `BIG100`
  (`fixed`, 10 000), ТОДІ `couponDiscountKopecks = 5 000` (обрізано до залишку),
  товари = 0, `shippingKopecks = 4 900`, `totalKopecks = 4 900` — підсумок
  **ніколи** не відʼємний і знижка не покриває доставку.

- **AC-12 (граничний — порожнє замовлення, D-14):** КОЛИ `order.items = []`,
  `customerTier = "gold"`, `coupons = ["ORDER10"]`, ТОДІ
  `subtotalKopecks = 0`, `tierDiscountKopecks = 0`, `couponDiscountKopecks = 0`,
  `shippingKopecks = 0`, `totalKopecks = 0`, `ORDER10` — у `rejectedCoupons`
  з причиною `no_matching_items`; винятку немає.

- **AC-13 (граничний — пів копійки, D-4):** КОЛИ замовлення `UA` з однієї
  позиції `unitPriceKopecks = 1 350`, `quantity = 3` (subtotal 4 050) від
  `silver`-клієнта, ТОДІ 5% = 202.5 коп. → `tierDiscountKopecks = 203`
  (half-up, **не** 202), товари = 3 847, `totalKopecks = 8 747`.

- **AC-14 (граничний — округлення бази категорії, D-4/D-5):** КОЛИ subtotal =
  10 001 (`standard` 5 000 + `fresh` 5 001), клієнт `silver`
  (`tierDiscountKopecks = round(500.05) = 500`, залишок 9 501), промокод
  `FRESH10` (`percent` 10, `fresh`), ТОДІ база категорії =
  `round(5 001 × 9 501 / 10 001) = 4 751`, `couponDiscountKopecks = round(475.1) = 475`,
  товари = 9 026, `totalKopecks = 13 926`.

- **AC-15 (невідомий код, D-10):** КОЛИ введено `["NOPE"]`, якого немає в
  каталозі, ТОДІ `rejectedCoupons = [{ code: "NOPE", reason: "unknown" }]`,
  знижки за промокодами 0, розрахунок успішний.

- **AC-16 (дубль коду, D-11):** КОЛИ введено `["ORDER10", "ORDER10"]` на
  замовленні 100 000 коп. від клієнта `none`, ТОДІ знижка застосована **один
  раз** (`couponDiscountKopecks = 10 000`), друге входження — у
  `rejectedCoupons` з причиною `duplicate_code`, `totalKopecks = 94 900`.

- **AC-17 (категорії немає в кошику, D-12):** КОЛИ замовлення містить лише
  `standard`-позиції, а введено `FRESH20` (`category: "fresh"`), ТОДІ промокод
  у `rejectedCoupons` з причиною `no_matching_items` і **не** зʼявляється в
  `appliedCoupons` зі знижкою 0.

- **AC-18 (невалідний промокод, D-13):** КОЛИ каталог містить `BAD150`
  (`percent`, value 150) або `NEG` (`fixed`, value −100), ТОДІ кожен із них
  відхиляється з причиною `invalid_value`; знижка не застосовується й не
  кліпується до 100%.

- **AC-19 (доставка недоторкана, D-16):** КОЛИ замовлення складається лише з
  `digital`-позицій на 100 000 коп. від `gold` з промокодом `ORDER10`, ТОДІ
  `shippingKopecks = 0`, `tierDiscountKopecks = 10 000`,
  `couponDiscountKopecks = 9 000`, `totalKopecks = 81 000`.

- **AC-20 (інваріант балансу, D-4):** ДЛЯ БУДЬ-ЯКОГО результату розрахунку
  ЗАВЖДИ виконується: усі поля — цілі невідʼємні числа, і
  `subtotalKopecks − tierDiscountKopecks − couponDiscountKopecks + shippingKopecks === totalKopecks`,
  а `couponDiscountKopecks === сума discountKopecks по appliedCoupons`.

> Граничні критерії: **AC-11** (знижка більша за суму), **AC-12** (порожнє
> замовлення), **AC-13** і **AC-14** (пів копійки / округлення бази).

## 5. Контракт

Типи `Order`, `LineItem`, `Coupon` беруться з `app/src/types.ts` без змін.
Нове живе в `app/src/discounts.ts`.

```ts
import type { Order, Coupon } from "./types.js";

export type CouponRejectionReason =
  | "unknown"            // коду немає в каталозі (D-10)
  | "duplicate_code"     // той самий код введено повторно (D-11)
  | "invalid_value"      // percent поза 0–100, fixed <= 0 (D-13)
  | "expired"            // now >= expiresAt (D-8, D-9)
  | "below_min_subtotal" // subtotal < minSubtotalKopecks (D-6)
  | "duplicate_scope"    // на цей скоуп промокод уже застосовано (D-3)
  | "no_matching_items"; // база знижки = 0 (D-12, D-14)

export interface AppliedCoupon {
  code: string;
  /** Фактично надана знижка в цілих копійках, після обрізання до залишку. */
  discountKopecks: number;
}

export interface RejectedCoupon {
  code: string;
  reason: CouponRejectionReason;
}

export interface PriceBreakdown {
  subtotalKopecks: number;
  tierPercent: number;
  tierDiscountKopecks: number;
  /** Сума discountKopecks по appliedCoupons. */
  couponDiscountKopecks: number;
  /** Товари після всіх знижок, >= 0. */
  discountedGoodsKopecks: number;
  shippingKopecks: number;
  /** discountedGoodsKopecks + shippingKopecks. Ніколи не відʼємний. */
  totalKopecks: number;
  /** У порядку введення клієнтом. */
  appliedCoupons: AppliedCoupon[];
  /** У порядку введення клієнтом. */
  rejectedCoupons: RejectedCoupon[];
}

/**
 * Єдина публічна точка входу. Ніколи не кидає винятків (D-8).
 * @param catalog усі відомі системі промокоди; зіставлення з order.coupons за code (точний збіг).
 * @param now момент розрахунку; за замовчуванням new Date() (D-9).
 */
export function priceOrder(
  order: Order,
  catalog: Coupon[],
  now?: Date,
): PriceBreakdown;
```

Допоміжне (може бути експортоване для тестів округлення, D-4):

```ts
/** Half-up від нуля: 202.5 → 203. */
export function roundKopecks(value: number): number;
```

### Алгоритм (нормативний)

1. `subtotal = subtotalKopecks(order)`; `remaining = subtotal`.
2. `tierDiscount = min(remaining, roundKopecks(subtotal × tierPercent(order) / 100))`;
   `remaining -= tierDiscount`.
3. Для кожного коду з `order.coupons` **у порядку введення** — перевірки в
   порядку D-17; при успіху:
   - база: без категорії — `remaining`; з категорією —
     `roundKopecks(categorySubtotal × remaining / subtotal)` (0, якщо `subtotal === 0`);
   - `raw = kind === "percent" ? roundKopecks(base × value / 100) : value`;
   - `discount = min(raw, base, remaining)`;
   - якщо `base === 0` → `no_matching_items`; якщо `discount === 0` при `base > 0`
     (напр. 0.4 коп. округлилось до 0) → промокод вважається застосованим зі
     знижкою 0 і скоуп займається;
   - `remaining -= discount`; скоуп позначається використаним.
4. `shipping = shippingKopecks(order)` (від вихідного замовлення);
   `total = remaining + shipping`.
