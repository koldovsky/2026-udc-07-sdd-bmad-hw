# Специфікація: Система знижок і промокодів

**Статус:** agreed
**Джерело:** `materials/feature-request.md`
**Автор рішень:** McLoy

---

## 1. Мета

Надати користувачам можливість застосовувати знижки через рівні лояльності (Silver 5%, Gold 10%) та промокоди (відсоток або фіксована сума). Система повинна коректно комбінувати різні типи знижок, обробляти граничні випадки, та забезпечити точність розрахунків до копійки.

## 2. Поза скоупом

- Керування промокодами (створення, видалення, редагування) — адмінка
- A/B тестування знижок — відбір користувачів
- Історія знижок у профілі користувача
- Сезонна конфігурація знижок — окремий сервіс
- Інтеграція з маркетинг-системами

## 3. Рішення щодо неоднозначностей

| # | Питання | Рішення | Чому саме так |
|---|---|---|---|
| D-1 | Як комбінуються рівень лояльності і промокоди? | **Послідовно:** спершу применяється рівень, потім кожен промокод послідовно до результату попереднього | Розраховуючи по етапах, клієнт отримує передбачувану знижку і розуміє, як вона складається. Одночасна сума (10% + 15% = 25%) при великих знижках перевищивши б очікування |
| D-2 | База для розрахунку знижки — товари, чи товари + доставка? | **Тільки товари (subtotal).** Доставка — окрема лінія в рахунку. Знижки не применяються до доставки | Доставка — це логістичні витрати, не залежить від вартості товарів. Користувач очікує, що 10% знижка — це від товарів, а не від доставки. Гарантує передбачуваність в UI |
| D-3 | Кілька промокодів на одну категорію — застосовуються всі, найвигідніший, або перший? | **Усі послідовно.** Якщо два промокоди на одну категорію, другий применяється до суми після першого (на цій же категорії) | Клієнт може комбінувати відповідні промокоди для максимальної вигоди (флеш + кешбек). Послідовність дає передбачуваний результат: другий промокод працює на меншій базі |
| D-4 | Округлення: де, до якої сторони, й що з пів копійками? | **На підсумку** після всіх знижок. **До найближчого цілого** (0.5 → 1, 0.4 → 0). Відсотки рахуються з дробами, потім результат округляється один раз | Округлювання на кожному рядку накопичує похибку. Одиночне округлення на підсумку забезпечує точність ±1 копійка для системи, що видно користувачеві |
| D-5 | Промокод на конкретну категорію — рахується від суми тієї категорії чи від всього замовлення? | **Від суми тієї категорії.** Якщо промокод має `category: "fresh"`, знижка рахується від суми всіх fresh-товарів в замовленні | Категорійні промокоди призначені для стимулювання покупок у конкретній категорії. Процент від всього замовлення змовчує цей намір |
| D-6 | Мінімальна сума для промокоду перевіряється до чи після інших знижок? | **До применення** цього промокоду і всіх наступних. minSubtotalKopecks порівнюється із поточною базою (subtotal після попередніх знижок) | Мінімум — це умова активації, а не фінальна сума. Якщо клієнт уже має знижку від рівня, це не дисквалифікує його промокод, а дозволяє скоротити знижку |
| D-7 | Чи може підсумок стати відʼємним? | **Не може.** Підсумок до сплати ≥ 0 копійок. Якщо сума знижок перевищує subtotal, результат = 0 копійок (замовлення безкоштовне) | Від'ємна ціна — це операційна помилка, не матиме сенсу для касира чи API. Нульова сума легальна (подарункові карти, промо-замовлення) |
| D-8 | Прострочений промокод — тиха відмова чи явна помилка для користувача? | **Тиха відмова.** Промокод з `expiresAt < today` просто ігнорується. Помилка видається в API як невідповідний код (`invalid_coupon`) під час валідації, але при розрахунку ціни просто пропускається | Фронтенд робить валідацію при введенні і показує помилку (UX). Бекенд не повинен падати на застарілому коді, може трапитися гонка часу. Тиха відмова захищає від того, що старий промокод раптом перестане працювати |
| D-9 | Промокод на категорію, якої немає в замовленні — ігнорується чи помилка? | **Ігнорується.** Якщо промокод має `category: "fresh"`, але в замовленні немає fresh-товарів, промокод просто не применяється (знижка = 0) | Користувач мав змішаний картрик до чекауту, потім видалив fresh-товари. Промокод все ще в полі вводу — не каралася помилкою, просто не дає знижку |
| D-10 | Порядок операцій для категорійного промокоду: рахувати від категорії перед чи після рівня? | **Рівень применяється до всієї суми, потім категорійний промокод рахується від суми тієї категорії після рівня** | Рівень — глобальна знижка, категорійні промокоди — локальні. Если рахувати категорійний промокод від оригінальної суми, рівень місцями буде перекритий |
| D-11 | Що лічиться базою для мінімальної суми (minSubtotalKopecks) — оригінальна сума замовлення чи після попередніх знижок? | **Оригінальна сума замовлення (order subtotal).** minSubtotalKopecks перевіряється один раз на початку, не змінюється при кожному промокоді | Більшість магазинів рахують мінімум від оригінальної вартості, щоб запобігти експлуатації (два малих промокоди обходять мінімум). Простіше реалізувати й пояснити |
| D-12 | Порожнє замовлення (без товарів) — коректно опрацьовується, чи помилка? | **Коректно опрацьовується.** Subtotal = 0, всі знижки = 0, total = shipping (або 0, якщо digital). Промокоди не применяються (не проходять minSubtotal) | Технічно можливо (API-запит), не повинна бути помилкою. Показує, що система звукова |
| D-13 | Два промокоди на одну категорію без категорії vs глобальні промокоди — чи вони окремо обробляються? | **Глобальні промокоди (без category) і категорійні (з category) применяються в одному ланцюзі послідовно.** Глобальний промокод рахується від поточного subtotal, категорійний — від суми своєї категорії, але після попередніх знижок | Унісон — один алгоритм для обох. Порядок — у рядку вводу (coupons[]) |

## 4. Критерії приймання

- **AC-1:** КОЛИ замовлення Gold-клієнта за 1 000 грн (100 000 копійок) без промокодів, ТОДІ знижка від рівня = 10 000 копійок, до сплати 90 000 копійок + доставка 4 900 копійок = 94 900 копійок

- **AC-2:** КОЛИ промокод прострочений (expiresAt = вчора), ТОДІ промокод ігнорується, ціна розраховується без нього

- **AC-3:** КОЛИ введено два промокоди на одну категорію (fresh -10%, fresh -20%), базова сума fresh = 500 грн (50 000 копійок), ТОДІ спершу 50 000 - 5 000 = 45 000, потім 45 000 - 9 000 = 36 000, знижка в сумі = 14 000 копійок

- **AC-4:** КОЛИ знижка перевищує subtotal замовлення (промокод -500 грн на замовленні 200 грн), ТОДІ до сплати = 0 копійок (замовлення безкоштовне, доставка окремо)

- **AC-5:** КОЛИ промокод з minSubtotalKopecks = 100 000 на замовленні за 80 000 копійок, ТОДІ промокод не применяється

- **AC-6:** КОЛИ рівень (10% Gold) + промокод (-15%), базова сума 1 000 грн, ТОДІ спершу 1 000 - 100 = 900 грн, потім 900 - 135 = 765 грн, до сплати 765 грн + доставка

- **AC-7:** КОЛИ промокод на категорію fresh (-10%), але в замовленні немає fresh-товарів, ТОДІ промокод не дає знижки (знижка = 0)

- **AC-8:** КОЛИ результат округлення з дробами: Silver рівень (5%) на 333 копійки = 16.65 копійок знижки, ТОДІ округлюється до 17 копійок, до сплати 316 копійок

- **AC-9:** КОЛИ послідовно применяються три промокоди (10%, 20%, 5% до категорії) на замовленні 1 000 грн, ТОДІ всі три зменшують суму послідовно без обмежень, якщо всі інші умови виконані

- **AC-10:** КОЛИ порожнє замовлення (без товарів, subtotal = 0), ТОДІ знижки не применяються (всі промокоди перевищують мінімум), до сплати = 0 (або доставка, якщо фізичні товари б були)

## 5. Контракт

```ts
export interface PriceBreakdown {
  subtotalKopecks: number;           // Сума товарів до знижок
  tierDiscountKopecks: number;        // Знижка від рівня лояльності
  couponDiscountKopecks: number;      // Сума знижок від усіх промокодів
  shippingKopecks: number;            // Доставка (не включена в знижки)
  totalKopecks: number;               // Разом до сплати
}

export function discountPrice(
  order: Order,
  coupons: Coupon[],
  today?: string
): PriceBreakdown
```

Параметри:
- `order` — замовлення з товарами і рівнем клієнта
- `coupons` — масив валідних промокодів, отриманих із бази за кодами з `order.coupons`
- `today` — поточна дата (ISO, за замовчуванням нині); потрібна для перевірки expiresAt

Повертає:
- `subtotalKopecks` — без змін, для UI (показати оригіналь)
- `tierDiscountKopecks` — знижка від `tierPercent(order)` на subtotal
- `couponDiscountKopecks` — сума всіх промокодів послідовно (не вмісщує tierDiscount)
- `shippingKopecks` — як є у `shippingKopecks(order)`
- `totalKopecks` — до сплати: `subtotalKopecks - tierDiscountKopecks - couponDiscountKopecks + shippingKopecks`, ≥ 0
